- [bug] **2026-08-04 phantom-order incident — cleaned up 2026-08-06.** An admin unlinked the three order forms and re-linked them into one consolidated spreadsheet (one tab per form). Google replayed each tab's full response history through the single bound `onFormSubmit` trigger, which pushed 117 historical form responses (order dates 2024-07-01 → 2026-07-21) into `orders` as new Pending rows — 88 predating the app entirely, 29 duplicates of already-Fulfilled `PU-` orders. Open-order demand was 88% phantom (815 of 2212 case-units) for two days. Verified against the 2026-07-08 backup that **nothing existing was overwritten or reverted** (34 status changes, all Pending→Fulfilled; zero customer/item/date/notes edits) and no POs were generated off the inflated demand. Deleted the 117 replay rows (pinned to the 15:00–16:00 UTC burst window, not to `Unknown Customer`, because an admin had begun hand-correcting rows and erasing that marker); repaired the 8 genuine post-incident submissions and re-keyed them `GF-` → `PU-` so the fixed script is idempotent against them. Result: 947 → 830 orders, 142 → 25 open, 0 `Unknown Customer`, 0 duplicate ids. Rollback manifest with full row contents saved in the session scratchpad. Root causes found in `Code.gs` and fixed in `apps-script/order-form-sync.gs` (v2): hardcoded `"GF-"` prefix across four tabs sharing a `merge-duplicates` upsert (silent overwrite hazard, already live — Sukhadia was `GF-...-3` from the NY tab while the Self-Distro tab also has a row 3); hardcoded `data["Business Name"]` vs the wholesale tab's `Distributor Name`; `getActiveSheet()` instead of `e.range.getSheet()`; `toISOString()` rolling every post-8pm-ET order to the next day; `parseInt` turning the free-text cell `"150 cases, wheat wrapper"` into qty 150; missing `Curried`/`Korean BBQ` product mappings; and a catch-all that logged errors so failed runs still reported "Completed". v2 adds a 30-day replay guard, per-tab config with unique prefixes, fail-loud behavior, and `validateConfig()`.
- [chore] Google Form → order-type tagging: resolved by hard-coding the type in the dedicated form's Apps Script, NOT in the app. Investigation (session 2026-07-22) found order type is not form-determined in the data — the `GF` prefix / `[via Google Form]` note is shared across multiple forms and holds both `NY Route` and `Self-distro`; `PU` (`[via Google Form Pickup]`) holds `Distributor` + `Self-distro`; the same customers appear under multiple forms. So there is no unique per-form signal in stored orders and no app-side auto-tag can separate them. Decision: dedicated forms (e.g. the CT/NY/NJ = NY Route form) stamp `order_type` directly in their bound script, and use a UNIQUE `ID_PREFIX` (NY Route = `NYR-`) so IDs don't collide with the shared-`GF` forms under merge-duplicates. An app-side prefix→type config UI was built (v185) then reverted (commit `20ca2c1`) as the wrong model for this data.
